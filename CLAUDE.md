# Line Follower Robot (ESP32-S3) — Project Brief

Speed-race line follower for an Industrial Design course. At the end of the semester all robots race on the same track and the fastest wins. Firmware runs on an ESP32-S3, with live telemetry to a phone and automatic lap timing.

## Goals (priority order)
1. Robot follows the line reliably and fast.
2. Smooth live telemetry on a phone with no external server.
3. Automatic lap timing measured on the robot.
4. Code structured so the sensor array and PID can be upgraded later without rewrites.

## Hardware
- **MCU:** YD ESP32-S3 (N16R8)
- **Motor driver:** DRV8833 (J2 jumpered, motors confirmed working)
- **Motors:** N20, **rated 3 V** (new motors with a different reduction, 2026-10-21; encoders no longer used). **Since 2026-10-23 the DRV8833 VM runs straight from the 2S battery** (user's choice; the MINI560 only feeds the ESP32, IR array and INA219). PWM is capped at 3 / 8.4 = 36 % (`MAX_DUTY` = `MOTOR_RATED_V / MOTOR_SUPPLY_V`, `MOTOR_SUPPLY_V` 8.4 = full 2S), so the motors never exceed 3 V; top speed sags with the battery (7.4 V → 2.6 V) because nothing measures the battery voltage. Before the change the motors were briefly run on 2S with the old 5 V cap (60 % → up to 5 V on 3 V motors).
- **Battery:** 2S 18650 Li-ion (8.4 V full), KCD1 rocker switch on battery +
- **Regulator:** MINI560 5 V buck
- **Current sensor:** INA219 (I2C) — **not used in code yet, not in the schematic**
- **Sensors:** **8-channel QTR-8A clone** (board "V2766", "8 sensor lines follow", pins VCC, D8..D1, IR, GND), in the code since 2026-10-21. **Confirmed analog**: each channel is a phototransistor with a 10 kΩ pull-up ("103" arrays) and a 220 Ω series resistor ("221" arrays), no comparators. At ~3 mm on 3.3 V: white 0.3 V, black 2.8 V. Its 3.3V pads are bridged, so it must stay on **3.3 V** (5 V would overdrive the LEDs). IR pin = LED enable, pulled on by R6 (47 kΩ). Replaced the 5-channel digital array (comparator + potentiometers). Possibly a custom 16-channel array later.
- **Track:** Cytron Reconfigurable Line Following Track, black line 18 mm wide
- **Build system:** PlatformIO (`platformio.ini`, espressif32@6.13.0 = Arduino core 2.0.17)

### Power (from schematic Sheet_1 rev 1.0)
Originally a single +5 V rail (MINI560 output, through the rocker switch) fed the ESP32 5V pin, DRV8833 VCC, the IR array, and both encoder VCCs. **Changed 2026-10-23: the DRV8833 VM is on the 2S battery directly** (see Motors), so `MAX_DUTY` now protects the 3 V motors from overvoltage. **Battery estimate consequence:** the INA219 shunt sits on the 5 V rail, so motor current no longer passes through it; the phone's battery % and time left only count the ESP32/sensor load and will read far too optimistic until the INA219 is moved to the battery line.

**Resolved (user, 2026-10-15):** the IR array and encoder outputs no longer drive the 3.3 V-only GPIOs with 5 V. The schematic (including the 2026-10-16 version) still shows the IR array and encoder VCC on +5 V.

**INA219 (schematic 2026-10-16):** VCC from the ESP32 3V3 pin, SDA 41 / SCL 42, shunt (Vin+ → Vin−) in series between the rocker switch and the +5 V rail. In that position it measures the **regulated 5 V rail and total robot current**, not the battery, so it can't give battery voltage or charge state. It can't be moved: the **BMS and MINI560 are mounted on the battery pack, off the board**; only 5 V reaches the board.

**IR sensor pins must be ADC1 (GPIO 1–10, not strapping pin 3).** ADC2 (GPIO 11–20) can't be read while Wi-Fi is on; `sensors.cpp` has a `static_assert` that fails the build otherwise. The user first wired D6–D8 to GPIO 12/13/14 and **rewired them to 7/8/9** (confirmed 2026-10-22). **D1 is the rightmost sensor** (looking from behind, confirmed with sensortest 2026-10-22), so `PIN_IR` runs D8..D1. Encoders are no longer wired.

**Motor direction (new 3 V motors, motortest 2026-10-22): neither motor is inverted** (`MOTOR_L_INVERT = false`, `MOTOR_R_INVERT = false`). The old motors needed the left one inverted.

History, old 5-channel digital array (sensortest, twice): O1 was the leftmost sensor. The old digital array output LOW on black (setting removed with it). Lesson kept: check sensor polarity with the in-air test (no reflection = black), not a guess.

Line colour is **switched on the phone** ("White line / Black line" in the Sensors card, message `0x15`, built 2026-10-22) and saved in NVS (namespace `sensors`, key `white`; saved when not driving). `LINE_IS_WHITE` (`true` = white line on a dark surface) is only the default before a colour is saved. Calibration measures two readings per sensor and the colour says which one is the line (auto-detecting the colour from the spin was tried earlier the same day and replaced, so a wrong guess can't flip it). Changing colour swaps each sensor's background/line readings (`sensorsSetCalibration()` normalises to the colour), so **no recalibration is needed after a switch**. The phone's request goes through `std::atomic` `wantWhite`; `readPosition()` on core 1 applies it, so only core 1 rewrites the calibration. Hello carries `"white"`; every phone gets `{"type":"line","white":..}` after a switch. Sensor bits always mean "on the line", whatever the colour.

### Next hardware: PCB as chassis (in development, schematic final 2026-10-24)
Schematic: `schematic/pcb_chassis_sheet1.png`. The PCB doubles as the chassis to save weight for high-rpm, low-torque motors. Plan: build it on a breadboard first, design the PCB once it works. **Firmware support built 2026-10-28** (user asked, from the schematic): `BOARD` in `config.h` = `Board::PcbChassis` (default) or `Board::Original` (the current robot). Sensor, motor and I2C pins are identical on both boards (checked against the schematic: D1..D8 = GPIO 1, 2, 4, 5, 6, 7, 8, 9; DRV8833 IN1/IN2 = 18/17 → right, IN3/IN4 = 16/15 → left; SDA 41 / SCL 42). Differences from the current build:
- **DRV8833 VCC on the battery side** (`DRIVER` net = MINI560 IN+, after the INA219), on purpose: the driver handles it, and PWM is limited per motor's rated voltage. **Firmware:** the power task low-passes the INA219 bus voltage (Vin− = the DRV8833's VM) and hands it to `motorsSetSupplyVoltage()`; duty = limit / that voltage, so the motors get exactly 3 V (or the dev unlock) at any charge. A rise is taken at once and a drop over `MOTOR_SUPPLY_FILTER_MS` (200 ms), so the duty errs low. A missing or impossible reading (outside `MOTOR_SUPPLY_MIN_V`..`MAX_V`, 5.5–9 V) falls back to `MOTOR_SUPPLY_V` (8.4 V) = slower, never faster. Host-tested: 8.4/7.4/6.4 V → 35.7/40.6/46.9 % duty = 3.00 V; faults (NaN, 0 V, 30 V, a 5 V rail) → 35.7 %.
- **INA219 between SW1 (MST-12D18G4 slide switch) and the battery-side node**, so it measures pack voltage and total current, motors included. **Firmware:** `power.cpp` uses Vin+ × I as battery power (no `BUCK_EFFICIENCY`), battery low = pack below `BATTERY_LOW_V` (6.4 V) for 2 s under load; the phone's Battery card labels the voltage "Battery" (hello `"inaBattery"`). % is still energy-counted (could use voltage later).
- **IR LED enable on GPIO 10** (`PIN_IR_LED` follows `BOARD`; 11 on Original). On Original, GPIO 10 is unused; the array's R6 pull-up keeps its LEDs on either way.
- **DRV8833 `EEP` (nSLEEP) unconnected on the schematic**: the module's J2 jumper must stay fitted to enable the driver, or the motors never run.
- **Encoder connectors kept** (C2-R / C1-R / C1-L / C2-L on GPIO 11 / 12 / 13 / 14, encoder VCC +5 V) so the old encoder motors can be swapped back in. Check that encoder outputs don't reach 5 V before using them. **Firmware:** `PIN_ENC_*` in `config.h`, never driven (plain inputs), no encoder code yet.
- DRV8833 `ULT` (nFAULT) left unconnected (user decision).

## Constraints and decisions
- **Analog sensor reading** (since 2026-10-21, with the QTR-8A clone). Digital reading was used first.
- **No PID at first.** Start with simple proportional control, then add D, then I only if needed.
- **No encoders in the code for now.** Leave clean stubs or hooks so they can be added later. (INA219 approved by the user and built 2026-10-16, see Battery estimate below.)
- **Motor voltage cap: 3 V, dev unlock up to 5 V.** All speeds (code, tuning, phone) are fractions of the motor voltage limit: 1.0 / 100 % = the limit, normally the rated 3 V. `motors.cpp` multiplies by the runtime `maxDuty` (= limit / supply: measured on PcbChassis, else `MOTOR_SUPPLY_V`; starts at `MAX_DUTY` 0.357) when setting PWM. **Dev unlock (built 2026-10-23, user request):** the phone's "Dev · motor voltage" card raises the limit up to `MOTOR_UNLOCK_MAX_V` (5 V) via message `0x16` (`motorsSetVoltageLimit()`, `std::atomic<float>`, clamped, NaN → rated); every speed scales with it, the phone's volt readouts follow (`motorV` = limit), going above 3 V asks for confirmation, and **it's not saved: every power-on starts at 3 V** (deliberate, so the motors can't stay overdriven by accident). Host-tested: 3 V → 35.7 % duty, 5 V → 59.5 %. Telemetry "duty" fields carry these speeds (after trim). Cruising speed is `BASE_SPEED`.
- **Boots in Stop** (`BOOT_MODE`, user, 2026-10-22; it used to start Auto by itself): the robot doesn't move after power-on or upload until a mode is picked on the phone. The motors also stay off for `START_DELAY_MS` (3 s) after boot in every mode.
- Spend no more money: use only the ESP32-S3 on the robot (no extra MCUs or computers).

## Architecture

### Dual-core split
- **Core 1: control loop.** Sensors, `readPosition()`, control, motor output, lap detection. Fixed period (start at 1–2 ms) using `micros()` or a hardware timer so `dt` is consistent.
- **Core 0: network.** Wi-Fi, web server, WebSocket, telemetry sending. Create the telemetry task with `xTaskCreatePinnedToCore(..., 0)`.
- If using ESPAsyncWebServer, make sure the AsyncTCP task runs on core 0 (check `CONFIG_ASYNC_TCP_RUNNING_CORE`), so it does not steal time from the control loop.
- The control loop must never call network functions and never wait on telemetry.
- Share data through a small struct that the control loop writes and the telemetry task copies (short critical section) or a length-1 overwrite queue. Always send the **latest** sample; drop old ones.

### Sensor abstraction
- All line-position logic lives behind `readPosition()`, which returns the line position as a number.
- Digital version: weighted average of the active sensors, e.g. weights `-4, -2, 0, +2, +4` for 5 sensors (adjacent pairs give in-between values).
- Include a **lost-line fallback**: when no sensor sees the line, keep turning toward the last known direction.
- **Analog version (built 2026-10-21, `src/sensors.cpp`):** 12-bit `analogRead` of 8 channels per tick. Each raw value maps through its calibration (background → 0, line → 1, either polarity) to a level 0..1. Position = level-weighted average of weights −7…+7 (levels < `IR_NOISE_FLOOR` ignored), scaled to ±1. Lost when no level > `IR_ON_LINE`; it then returns ±1 toward the last side (`lastSide`, see Sharp corners). The analog array never reports `InGap` (that was for the old digital array, whose line could sit between sensors).
- **Calibration (reworked 2026-10-22, so the array height doesn't matter):** phone "Calibrate" button = mode `Calibrate` (3). The control task spins right/left/right for `CAL_DURATION_MS` at the phone's "Calibrate spin speed" slider (Tuning `calSpeed`, default `CAL_SPIN_SPEED` 1.0 = full speed since 2026-10-22, was 0.5) while `readPosition()` fills a histogram per sensor (32 raw counts per bin), then switches to Stop. `sensorsCalibrateEnd()` splits each histogram into two groups with Otsu's method (each group ≥ 1 % of samples, so stray readings can't pose as the line) and stores the group **averages** as `background` / `line` (not min/max, which one stray reading skews). On-line threshold = level 0.5 = halfway between them. `LINE_IS_WHITE` says which group is the line (raw is high over black). It fails (old calibration kept) if any sensor's groups are closer than `IR_CAL_MIN_CONTRAST` (250 ≈ 0.2 V; was a 600 min/max range, which failed at larger heights and silently left the 3 mm defaults in use). Result → `sharedCalibrationDone()` → telemetry task saves it to NVS (namespace `sensors`, `CAL_VERSION` 2, tied to a hash of the pins) and sends `{"type":"cal"}` with `white`, `bg[]`, `line[]`; the phone shows the line colour and the weakest sensor's line/background gap in volts (the margin left at that height). Loaded at boot in every build; defaults `IR_DEFAULT_WHITE/BLACK` (3 mm values) until calibrated. **Recalibrate after changing the array height.** Host test of the maths: compile `src/sensors.cpp` with a stub `Arduino.h` (not kept in the repo).
- Sample frame **version 2** adds the sensor count and one level byte per sensor (bytes 36+); the phone shows each sensor as a grey level.
- Make the sensor count and weights configurable so the 16-channel array and an analog version can replace it later without touching control or telemetry code.

### Control
- Position error → steering correction → left/right motor duty, clamped to `MAX_DUTY`.
- Gains (`KP`, `KD`, base speed) in `config.h`, and tunable live from the phone UI later.
- Filter the D term if added.
- **Built 2026-10-15:** PD in `controlUpdate()`. The derivative of position is low-pass filtered (`KD_FILTER_MS` = 10 ms) and reset by `controlReset()` whenever line following (re)starts (mode change, end of start delay, after a lost-line stop). `KD` defaults to 0 (P only) until tuned.
- **Sharp (90°) corners (built 2026-10-22):** when the line is Lost the robot **spins on the spot** (`PIVOT_SPEED` 0.6, wheels opposite) toward the side it went, until a sensor sees the line, then PD restarts with `controlReset()`. Brakes after `LOST_TIMEOUT_MS` (1500 ms, was 500) without the line. Before this, a lost line only meant PD at position ±1, a wide forward arc (inner wheel ~0.2 at speed 0.7, KP 0.4) that couldn't make a 90° corner. The side comes from `lastSide` in `readPosition()`: the outer sensor that last saw the line alone (the corner's side branch reaches it), else the last position beyond `LOST_SIDE_MIN` (0.2). Not just the sign of the last position, because at a corner the line can vanish under the middle sensors last. Phone status shows "Lost → turning left/right".
- **Corner brake (built 2026-10-22):** above ~50 % speed the robot slid too far past a 90° corner for the spin to swing the array back onto the side branch (KP doesn't help: it's momentum). Now both wheels go **full reverse for `cornerBrakeMs`**, once per corner, when the corner shows (`sensorsCorner()`: ≥ `CORNER_MIN_SENSORS` (4) on the line reaching exactly one outer sensor; a cross reaches both and doesn't count) or when the line is lost. Re-arms after `CORNER_REARM_MS` (200 ms) of plain line following, so it can't fire twice per corner or from a standstill; disarmed outside Auto. `cornerBrake()` in `control_task.cpp`.
- **Corner brake and spin speed are live sliders** (Tuning fields `cornerBrakeMs` 0–300 ms, default `CORNER_BRAKE_MS` 40; `pivotSpeed` 0.1–1, default `PIVOT_SPEED` 0.6). Message `0x12` is now 33 bytes with `calSpeed` last (a shorter one keeps the fields it lacks). Tuning record versions 1–3 (five, seven, eight fields) are migrated (`oldFields()`), so saved slider values survive updates. **When adding a Tuning field, append it, bump the version and add the old field count to `oldFields()`.** User's values on 2026-10-22: speed 0.5, KP 1.0, KD 0.005 turns 90° without the brake; 60 %+ with KP 1.5 didn't.
- **Position smoothing (built 2026-10-22, user saw the motors jitter on a straight):** `controlCorrection()` low-passes the position (`smoothMs`, default `POSITION_SMOOTH_MS` 4 ms, live slider "Smoothing", 0 = off) before KP and before the derivative. Cause: one raw ADC read per sensor per 1 ms tick; the noise reached the motors every tick and KD magnified it. Host simulation (position noise std 0.02, KP 1.0, KD 0.005): wheel command jitter 2.9 % → 0.9 % of speed at 4 ms, for ~4 ms of extra delay (8 ms: 0.6 %, 15 ms: 0.4 % but 16 ms delay). **Measured afterwards (sensortest, robot still, motors off, on USB): ADC noise is only ~1–2 counts std (5–8 mV p-p) on every sensor, so plain sensor noise is NOT the main cause.** Still open: motor electrical noise while driving, steppy position when the array is very close to the floor (each sensor fully on/off, position jumps between steps), or KP too high for the speed (saved Auto speed was 100 % then). Smoothing still softens derivative spikes from steps. Tuning record `RECORD_VERSION` 4 (version 3 = eight fields).
- **Hill crest / gap (built 2026-11-01, user: at the top of a hill the sensor boom sticks out over the crest and loses the surface):** before, that counted as Lost → corner brake (full reverse, could roll back down) + spin. Now `readPosition()` decides as the line goes: gone from the **middle** (|position| < `LOST_SIDE_MIN` and no outer sensor saw the line in the last `GAP_EDGE_RECENT_MS` 150 ms) → `LineState::InGap` (reused; the old digital-array meaning is gone), position 0; off a **side** → Lost as before. InGap in Auto: no corner brake, drive straight at Auto speed for `gapMs` (live slider "Hill / gap · drive straight", default `GAP_STRAIGHT_MS` 300 ms, 0–1000), then spin toward `sensorsLastSide()`; brakes after `LOST_TIMEOUT_MS` + gapMs. Center test: stops. Phone tag "Gap → straight". `GAP_TIMEOUT_MS` removed. Host-tested: crest (array lifted, raw 4095), slightly off-centre crest, dashed-line gap → straight; 90° corner and curve slide-off → Lost with the right side. On a black-line track a lifted array reads as all-line (position 0) and already drove straight. Tuning record `RECORD_VERSION` 5 (version 4 = nine fields).
- **Downhill slow-down after a crest: removed in v3 (2026-11-24).** v2 lowered Auto speed for a set time after a crest because, without encoders, gravity sped the robot up downhill. Speed control (below) now holds the speed down a slope itself, so the user asked for a clean version without it. Crest detection ("Gap → straight") stays.
- **Figure-8 crossings (built 2026-11-05, user: on an 8 layout the robot turned into the crossing line and looped):** at an angled crossing the other line reaches one side of the array first, so the position jumped toward it and PD steered onto it. Now `readPosition()` flags `sensorsCrossing()` when the bits form ≥ 2 separate patches or ≥ `CROSSING_MIN_SENSORS` (4) are on, and then returns the position from **before** (held), so the robot drives straight over. A 90° corner is wide too: held briefly, then its line runs out to that side and the Lost logic (edge seen recently, `lastSide`) brakes and spins into it as before. Frame flags bit 4 = crossing; phone tag "Crossing → straight". Host-tested: angled and square crossings → steer 0 throughout; 90° corner → Lost left; normal curve still steers (+0.57). The corner brake still fires when an angled crossing first reaches one edge (harmless slow-down). **Fixed 2026-11-24 (user: at a sharp right 90° the right sensors were lit but it spun left):** the hold froze `lastSeen`, so when the corner's branch stopped short of the outermost sensor the side fell back to the frozen pre-corner position (a slight left drift → left). Now a wide **single** patch leaning past `LOST_SIDE_MIN` (`branch` in `readPosition()`) sets `lastSide` from the live position and counts as an edge for the gap/corner decision; two patches or both edges (real crossings) still hold. Host-tested: right/left 90° with the branch short of the outer sensor after a drift the other way → correct side; crossings still straight; crest still a gap.
- **Long-straight slow-down: tried and removed (2026-11-10).** A timer on "line near the centre" can't tell a flat straight from a ramp, so it would also slow the robot on climbs and descents (user's verdict: unusable). Don't re-add it without a way to tell them apart. Tuning record version 7 existed only for it; `settingsLoad()` still reads a v7 record's first twelve fields so saved sliders survive.
- **Wheel encoders (built 2026-11-24):** the user swapped in encoder N20s (6 V encoder motors with the fast gearboxes fitted: **`MOTOR_RATED_V` = 6 V** since 2026-11-24, so 100 % = 6 V; dev unlock up to `MOTOR_UNLOCK_MAX_V` = 8.4 V = full battery; below the limit the duty clamps at 100 %). `src/encoders.cpp`: ESP32-S3 PCNT units 0 (left) / 1 (right), x4 quadrature (two channels per unit), glitch filter 1.25 µs; the 16-bit counters wrap at `ENC_PCNT_LIMIT` (10000) and `encodersUpdate()` (control task, every tick) folds them into 32-bit totals modulo the limit. Speed over `ENC_SPEED_WINDOW_MS` (20 ms) in mm/s, frame bytes 28/30 (i16), phone "Wheel speed L / R" (hello `"enc"`). **Measured with `enctest` (2026-11-24): 300 counts per wheel turn (L +303, R about −300), ~0.35 mm per count.** The hand test's signs were wrong (wheels turned the other way than driving forward): a real Learn run measured −3.5 m going forward, so **`ENC_L_INVERT = true`, `ENC_R_INVERT = false`** (fixed 2026-11-24). Check: in Manual, driving forward must show positive wheel speeds. Encoders powered from 3.3 V. Encoders only on `BOARD == PcbChassis` (`ENCODERS_FITTED`). Used by the speed control (below); next: braking to a target corner speed, then mapping.
- **Speed control / cruise (built 2026-11-24):** with encoders measured and slider "Speed control · target" > 0 (Tuning `cruiseMms`, default `CRUISE_MMS` 0 = off → fixed power from "Auto speed"), Auto's base speed comes from `controlCruise()`: PI on the average wheel speed with feed-forward `target / mmsAtFull`, where `mmsAtFull = SPEED_AT_FULL_MMS` (1500 mm/s at the rated 6 V, **an estimate: measure**) × voltage limit / rated; output clamped to `CRUISE_MIN_BASE` (−0.5, may brake downhill) .. 1, integral frozen while saturated (and while not following: brake, spin). Steering (`controlMix()`, same KP/KD mix) is added on top, unchanged. The straight drive over a crest uses the cruise too (full target speed). Sliders "Speed control · KP" (1.0, extra base per mm/s error × mmsAtFull) and "· KI" (4 /s). Host-simulated (first-order robot, tau 150 ms, 20 ms speed delay): 800 mm/s held within ~2–5 % on flat, ±12° slopes (power 53 / 73 / 33 %) and with 20 % weaker motors; an unreachable target saturates at 100 % and recovers without overshoot. Tuning `RECORD_VERSION` 9 (v3 dropped the two downhill fields from the middle). `settingsLoad()` reads every older record (v1–v8) via `oldLayout()`: the first ten common fields plus, from v8, the speed-control fields; each old record's hash is rebuilt from its own defaults (removed downhill / long-straight defaults kept as constants). Host-tested v3, v5–v9 and a stale-config v8 (ignored).
- **Track map: Learn / Race modes (built 2026-11-24, user asked for self-mapping):** `src/track_map.cpp`. **Learn** (mode 5) = Auto + recording: every `MAP_SEG_MM` (25 mm) of distance (average of both wheels, so spinning adds ~0) it stores the turn ratio |dL − dR| / (|dL| + |dR|) as a byte (0 straight … 255 spin on the spot); ends when the line is lost for good (`LOST_TIMEOUT_MS` → mode Stop) or the user taps Stop; kept if ≥ `MAP_MIN_SEGMENTS` (4 = 0.1 m, user 2026-11-24; was 20); the telemetry task saves it to NVS (namespace `map`, header version/count/segMm) when not driving and sends `{"type":"map"}`; loaded at boot. **Race** (mode 6) = Auto whose speed-control target comes from a plan made at the start of the run (`mapRaceBegin`): per segment `sqrt(grip × R)` with R = half wheel track (`WHEEL_TRACK_MM` 95, from the chassis) / turn ratio averaged over 3 segments (straight below `MAP_STRAIGHT_TURN` → "Race · top speed"); a segment with a spin (turn ≥ `MAP_CORNER_TURN` 0.6) is never averaged away → `MAP_MIN_MMS` 250; then a backward pass so it can brake in time (`sqrt(v_next² + 2·grip·seg)`). The target is read `MAP_LAG_S` (0.15 s) ahead. At each Lost (corner) the distance re-syncs to the nearest map corner within `MAP_SYNC_MM`. No timed corner brake in Race (the plan brakes); the reactive spin is unchanged. Sliders "Race · top speed" (default `RACE_TOP_MMS` 1000) and "Race · grip" (`RACE_GRIP` 2 m/s²). Phone: Learn/Race buttons, "Track map" card (metres, corners). Tuning `RECORD_VERSION` 10 (v9 = thirteen fields). Host-simulated (1 m straight, 90° spin, curve R 300, straight): 1 corner found; plan 1200 → 250 mm/s at the corner with braking from ~200 mm before, 945 mm/s in the R 300 curve; a 150 mm distance error re-synced at the corner. Needs a fixed start point; not tested on the track yet.
- **Defaults re-based on v1success for the 6 V motors (2026-11-24, user lost track of the many sliders and the robot stopped following the line):** same gearbox as the old 3 V motors, so v1success's values in volts: `BASE_SPEED` 0.25 (1.5 V), `KP` 0.50, `KD` 0.0025, `PIVOT_SPEED` 0.30, `CAL_SPIN_SPEED` 0.5, `MANUAL_MAX_SPEED` 0.5; speed control off. Changing them changes the defaults hash, so the saved sliders reset to these at the next boot (calibration and line colour kept). Plan agreed with the user: from here change one setting at a time.
- **Motor balance trim** (`MOTOR_TRIM`, `motorsSetTrim()`): > 0 slows the right motor, < 0 the left, applied in every mode. Default **0** for the new 3 V motors (the old 0.28 was measured on the previous motors). Telemetry speed is after trim.

## Telemetry

### Transport
- ESP32 runs as its **own Wi-Fi access point** and serves the web page itself (no external server, no internet).
- Phone joins the ESP32 Wi-Fi and opens `192.168.4.1`. Data streams over **WebSocket**.
- Disable Wi-Fi power saving (`WiFi.setSleep(false)`).

### Frame content
Send at a steady 30–50 Hz from the telemetry task, as a compact **binary** frame:
- timestamp (ms)
- sensor bits (1 byte, one bit per sensor)
- position / error
- left and right motor duty
- current lap number
- last lap time (ms)

Send lap completion as a separate **event message** so it is never lost to dropped frames. Reserve room in the frame format for later fields (speed from encoders, current/voltage from INA219).

### Implementation (Phases 3–5, built 2026-10-15)
- `src/control_task.cpp`: control loop task, core 1, priority `configMAX_PRIORITIES - 3`, paced by `vTaskDelayUntil` (1 ms tick, so `CONTROL_PERIOD_US` must be whole ms). Reads and publishes sensors during the start delay too, motors braked.
- `src/shared.cpp`: latest-sample mailbox (`portMUX` critical section, struct copy).
- `src/telemetry.cpp`: core 0 task. Wi-Fi AP `WIFI_SSID` / `WIFI_PASS` (in `config.h`), page on port 80, WebSocket on port 81 (library `links2004/WebSockets`, polled from this task, so no AsyncTCP core flag needed). The frame layout is documented in `src/telemetry.h`: type 1 sample, 36 bytes, little-endian, version 1. Sensor bits are **u16** (not 1 byte) so the 16-channel array fits. Bytes 28–35 are reserved for encoder speed and INA219. Type 2 (lap event) is reserved for Phase 6. A JSON `hello` text message on connect carries the sensor count and gains.
- `web/index.html`: the phone page, embedded with `board_build.embed_txtfiles` (edit the file, then rebuild). Served with `Cache-Control: no-store`, because phones kept showing the old page after an upload. Open it with `?demo` for fake data (`.claude/launch.json` → `phone-page` serves `web/` on port 8765).
- **OTA uploads (built 2026-10-28, user request):** `src/ota.cpp` (ArduinoOTA, port `OTA_PORT` 3232, hostname `line-follower`), started after the access point and polled from the network task. Password-protected: `[ota] password` in `platformio.ini` is compiled in (`-DOTA_PASSWORD`) and passed to the uploader. The Mac must **join the robot's Wi-Fi** (the robot is an access point, so the Mac loses internet meanwhile), then `pio run -e robot_ota -t upload` (espota to 192.168.4.1). An upload switches the robot to Stop first; the transfer blocks the network task, so telemetry pauses; it reboots into the new firmware (boots in Stop). The default 16 MB partition table already has two app slots (6.4 MB each). The first OTA-capable firmware had to go on over USB (done 2026-10-28). macOS may ask to allow incoming connections for Python during an OTA upload (espota listens for the robot to connect back): allow it.
- The frame also carries `loop max us` and `period max us` per 20-tick window, to prove Wi-Fi doesn't disturb the control loop.
- **ESP32 performance** (`src/sysmon.cpp`, built 2026-10-15): a `{"type":"stats"}` text message once a second with CPU load per core, control-loop load, free/lowest heap, free PSRAM, chip temperature, phone RSSI and uptime. FreeRTOS run-time stats are off in the Arduino core, so CPU load comes from idle hooks: each hook returns `false` (idle task keeps spinning, no wait-for-interrupt) and adds up gaps < 50 µs between its calls as idle time. This is an estimate: interrupts during idle count as idle.

## Drive modes and manual control (built 2026-10-15)
- Three modes chosen on the phone page: **Auto** (line following), **Manual** (on-screen joystick), **Stop** (motors braked, sensors and telemetry still live). Boot mode = `BOOT_MODE` in `config.h` (Stop). The start delay applies to every mode.
- Phone → robot messages over the same WebSocket (layout in `src/telemetry.h`): `0x10` set mode, `0x11` drive (throttle, steer). The command mailbox lives in `src/shared.cpp` (`sharedSetMode`, `sharedSetDrive`, `sharedCommand`).
- Manual mixing is in `controlManual()` (`src/control.cpp`): arcade mix, scaled together so the turn ratio is kept, capped at `MANUAL_MAX_SPEED` (1.0 = 3 V since 2026-10-22).
- **Dead-man:** the phone repeats drive commands at 30 Hz while in Manual. The robot brakes if none arrive for `MANUAL_TIMEOUT_MS` (300 ms): Wi-Fi drop, locked phone, closed tab. The phone also releases the stick when the page is hidden.
- The current mode is echoed in every sample frame (flags bits 1–3), so the page always shows what the robot is actually doing.
- **Center test** (mode `Hold` = 4, phone button "Center test", built 2026-10-22): bench test of the steering. No forward speed: `controlCorrection()` (the same PD as Auto, live KP/KD) clamped to ±1 drives the wheels opposite (`motorsSet(c, -c)`), so the robot turns on the spot to keep the line centred. The user slides or twists it off-centre and watches it come back (overshoot → lower KP / raise KD; slow or stops short → raise KP). Lost line: spins toward the remembered side like Auto, brakes after `LOST_TIMEOUT_MS`. No corner brake in this mode; no flash saves while it drives.
- **Live tuning sliders** (phone "Tuning" card, below the graph): Auto speed, Manual max speed, KP, KD, Motor balance, Corner brake, Corner spin speed, Calibrate spin speed, Smoothing, Hill / gap, Speed control target / KP / KI, Race top speed / grip. Message `0x12` carries all fifteen as f32; the robot clamps them in `sharedSetTuning()` (a separate `Tuning` mailbox), applies them in the control task each tick, and sends `{"type":"tuning"}` to every phone so sliders agree. The card also shows the matching `config.h` line.
- **Saved to flash** (`src/settings.cpp`, NVS namespace `tuning`, built 2026-10-15): loaded at boot in `main.cpp`. The telemetry task saves `TUNING_SAVE_DELAY_MS` (2 s) after the last slider change, skips writes that change nothing, and **never saves while Auto is driving** (a flash write pauses both cores); it waits until the robot stops. The record holds an FNV-1a hash of the `config.h` defaults, so **editing `config.h` defaults discards the saved values** at the next boot. The phone shows the save state (`"save"` in hello/tuning: saved, defaults, pending, waiting, error) and has a "Reset to config.h values" button (message `0x13`, erases the record).

## Battery estimate (built 2026-10-16)
- Battery: 2S 18650, **2600 mAh** each in series (`BATTERY_MAH`, `BATTERY_NOMINAL_V` 7.4 V, `BATTERY_USABLE` 0.9 → ~17.3 Wh usable). BMS and MINI560 are on the pack; the board only sees 5 V.
- `src/power.cpp`: own INA219 driver (no library), task on core 0 at 50 Hz, 0.1 Ω shunt, ±320 mV range, 16-sample averaging. Integrates battery energy = (Vin+ × I) / `BUCK_EFFICIENCY` (0.88). % = 1 − used / usable; time left uses a ~30 s power average.
- **PcbChassis: % from the pack voltage (built 2026-10-28, user wanted a real %).** `trackRestVoltage()` in `power.cpp`: resting voltage ≈ Vin+ (the pack; the shunt is outside it) + I × `BATTERY_INTERNAL_OHMS` (0.15 Ω guess for 2 cells + BMS + switch + wiring), low-passed over `BATTERY_FILTER_S` (20 s), then `chargeFromRestV()` interpolates a typical 18650 resting-voltage table (4.20 V/cell = 100 %, 3.84 = 50 %, 3.27 = 0 %) × `BATTERY_CELLS`. No battery (Vin+ < `BATTERY_PRESENT_V` 5 V, e.g. USB only) → `percent` −1, phone shows "—" / "No battery". No "Battery charged" press needed; that button only resets the energy-used counter there. Time left = % × usable Wh / average power. Host-tested: a 50 % pack stays at 50 % idle, at 1.2 A and with 2.5 A spikes (raw voltage alone would read 25 % / 8 %). **Tune `BATTERY_INTERNAL_OHMS` from real runs:** % dips while driving and recovers when stopped → raise it; % rises while driving → lower it. Stats carry `battFromV` and `battRestV`; the phone hint shows the resting estimate per cell.
- **Original: only correct if the phone's "Battery charged" button (message `0x14`) is pressed after each full charge.** Energy used is saved to NVS (namespace `battery`) about once a minute and right after a reset, never while Auto is driving (`powerService()` from the telemetry task).
- **Battery low** = MINI560 output (Vin+) below `RAIL_LOW_V` (4.75 V) for 2 s while current > 50 mA (Original); pack below `BATTERY_LOW_V` (6.4 V) on PcbChassis. Running on USB with the switch off draws no shunt current, so it neither counts energy nor triggers the warning.
- Frame bytes 32–35 carry 5 V rail mV and current mA live (0 if the INA219 isn't found); the 1 s `stats` message carries the battery fields. Phone: battery badge in the header plus a Battery card.

## Lap timing
- Measured **on the ESP32** with `micros()`, never on the phone.
- Detect a lap when all (or nearly all) sensors read black at the same time (start/finish bar wider than the line), confirmed over a couple of consecutive samples.
- Add a **lockout time** after each crossing (about 70% of the expected lap time) so one bar is not counted twice.
- First crossing starts the clock. Check the actual Cytron track layout for crossings or junctions that could cause false triggers; if there are any, discuss adding a side sensor with the user.
- The phone interpolates the running timer from the last lap-start event.

**Status: switched off** (`LAP_TIMING_ENABLED = false`, user decision 2026-10-15). The code below stays in place; the phone hides the lap cards when the `hello` message says `"laps":false`.

### Implementation (Phase 6, built 2026-10-15)
- **Lap marker = Cytron Cross tile** (user's decision; the competition track's marker doesn't matter). Its 18 mm perpendicular line spans the whole array.
- `src/lap_timer.cpp`, called from the control task only while running (not during the start delay). A crossing = at least `LAP_MIN_SENSORS` (all 5) sensors each saw black within the last `LAP_WINDOW_MS` (30 ms), so a robot crossing at an angle still counts. Lockout = `LAP_MIN_LOCKOUT_MS` (3 s) until the first lap, then `max(3 s, 0.7 × time between crossings)`. `LAP_CROSSINGS_PER_LAP` = 2 for a figure-8 through the cross.
- Events go control task → FreeRTOS queue (`sharedPushLap`, never blocks) → telemetry task → WebSocket type 2 message. The telemetry task keeps the history (200 events) and replays it to every phone that connects.
- Station tiles would also trigger a lap (all black), and T-junctions can pull the robot into the branch; keep them out of the practice layout.
